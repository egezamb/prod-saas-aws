# Design decisions

Why the estate is shaped the way it is — the trade-offs, stated honestly.

### ECS Fargate over EC2 or EKS
Fargate = no servers to patch or scale, pay per task. For a single-service SaaS
it's the least operational overhead. EKS (Kubernetes) is more powerful but far
more to run for one app; plain EC2 is cheaper but you own the host. Fargate is
the right middle for "production without a platform team."

### Public/private subnet split, app has no public IP
The ALB is the only thing on the internet. ECS tasks and RDS live in private
subnets and are reachable only through security groups (ALB → ECS → RDS). Smaller
attack surface, and it's the shape real environments use.

### One NAT gateway (and why it's the cost hook)
Private tasks need outbound internet (pull images, call APIs) → a NAT gateway.
It's a single NAT (not one per AZ) to save money; a true HA setup uses one per
AZ. It's also the biggest bill — see [COST.md](COST.md) for how to drop it with
VPC endpoints or public-subnet tasks.

### Secrets in SSM Parameter Store, injected at runtime
The DB password is generated by Terraform (`random_password`), written to SSM as
a **SecureString**, and referenced by the ECS task's `secrets` block — so it's
decrypted into the container's env at start. It never appears in the repo, the
image, or the task definition JSON. SSM (not Secrets Manager) because it's free
for standard parameters and enough here.

### TLS is optional via `certificate_arn`
Pass an ACM cert ARN → the ALB serves HTTPS and redirects HTTP→HTTPS. Leave it
empty → plain HTTP, so the reference runs with zero domain setup. Avoiding a
Route53/ACM-validation dependency keeps first-apply friction low; a real deploy
sets the cert.

### Target-tracking autoscaling on CPU
The service scales 2→6 tasks to hold CPU near 60%. Simple, predictable, and the
most common starting policy. Request-count-per-target is the next step if the
workload is I/O-bound rather than CPU-bound.

### Single-AZ RDS, `skip_final_snapshot`, no deletion protection
Deliberately **not** production-hardened, so it's cheap to spin up and tear down
while learning. Each of these has an inline comment in `rds.tf` telling you to
flip it for real production (Multi-AZ, final snapshot, deletion protection).

### Remote state left to the user
`versions.tf` ships the S3 backend commented out. State with secrets shouldn't
live on one laptop; configure S3 + DynamoDB locking before using this for real.
