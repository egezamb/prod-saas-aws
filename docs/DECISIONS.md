# Design decisions

Why the estate is shaped the way it is — the trade-offs, stated honestly.

### ECS Fargate over EC2 or EKS
Fargate = no servers to patch or scale, pay per task. For a single-service SaaS
it's the least operational overhead. EKS (Kubernetes) is more powerful but far
more to run for one app; plain EC2 is cheaper but you own the host. Fargate is
the right middle for "production without a platform team."

### Public/private subnet split, app has no public IP
The ALB is the only thing on the internet. ECS tasks and RDS live in private
subnets and are reachable only through security groups (ALB → ECS → RDS). Smaller
attack surface, and it's the shape real environments use.

### One NAT gateway (and why it's the cost hook)
Private tasks need outbound internet (pull images, call APIs) → a NAT gateway.
It's a single NAT (not one per AZ) to save money; a true HA setup uses one per
AZ. It's also the biggest bill — see [COST.md](COST.md) for how to drop it with
VPC endpoints or public-subnet tasks.

### Secrets in SSM Parameter Store, injected at runtime
The DB password is generated by Terraform (`random_password`), written to SSM as
a **SecureString**, and referenced by the ECS task's `secrets` block — so it's
decrypted into the container's env at start. It never appears in the repo, the
image, or the task definition JSON. SSM (not Secrets Manager) because it's free
for standard parameters and enough here.

### TLS is optional via `certificate_arn`
Pass an ACM cert ARN → the ALB serves HTTPS and redirects HTTP→HTTPS. Leave it
empty → plain HTTP, so the reference runs with zero domain setup. Avoiding a
Route53/ACM-validation dependency keeps first-apply friction low; a real deploy
sets the cert.

### Target-tracking autoscaling on CPU
The service scales 2→6 tasks to hold CPU near 60%. Simple, predictable, and the
most common starting policy. For an I/O-bound workload that stays under the CPU
target, set `requests_per_target` to the ALB requests-per-task you want to hold:
a second target-tracking policy is added alongside CPU, and autoscaling takes the
higher desired count of the two. It stays off (0) by default.

### Single-AZ RDS, safeguards behind `db_protect`
Deliberately **not** production-hardened by default, so it's cheap to spin up and
tear down while learning. `db_protect = true` turns on deletion protection and a
final snapshot together; Multi-AZ stays an inline flip in `rds.tf`. IAM token
sign-in is on, next to the password, so callers can move to short-lived tokens.

### Immutable image tags, and the first apply
ECR tags are immutable, so every running image traces back to one commit and
nothing can be pushed over it. Deploys push the commit SHA and register a new
task definition revision; the ECS service ignores `task_definition` changes so
`terraform apply` never rolls a deploy back. The very first apply creates the
ECR repository, so there is no image yet and that first deployment stops: push
`:latest` once by hand, then start a new deployment (`aws ecs update-service
--force-new-deployment`, or run the Deploy workflow). A changed task setting in
Terraform (CPU, env, secrets) reaches the service with the next deploy, which
bases its revision on the family's latest one.

### Accepted scanner findings
`trivy config` runs in CI. Three findings are accepted on purpose, each marked
with a `trivy:ignore` comment on its own resource, with the reason, so the same
finding on another resource still fails: the ALB is public (it is the front door), HTTP
is served when no `certificate_arn` is given (TLS is optional for a demo), and
tasks may reach any host on 443 (ECR, Secrets Manager and CloudWatch through the
NAT gateway; VPC endpoints would remove this, at their own hourly cost).

### Remote state left to the user
`versions.tf` ships the S3 backend commented out. The state holds the generated
database password, so it shouldn't live on one laptop. Before using this for real:

- **A bucket for state only:** versioning on (so a bad apply can be rolled back),
  public access blocked, and encrypted.
- **`use_lockfile = true`:** the S3 backend locks the state with a lock object in
  the bucket. It came in Terraform 1.10 and is generally available since 1.11, which
  also deprecated the DynamoDB locking arguments.
- **`terraform init -migrate-state`** moves an existing local state into the bucket.

### Notes for running this for real
- **Upgrading an older stack:** removing an inline `egress` block only stops
  Terraform from managing it, so a stack created before the narrowed egress rules
  keeps its old allow-all rule. Revoke it once per group:
  `aws ec2 revoke-security-group-egress --group-id <sg> --ip-permissions IpProtocol=-1,IpRanges=[{CidrIp=0.0.0.0/0}]`.
- **Rollback depth:** the ECR lifecycle policy keeps the last 10 images, so a
  rollback by task definition revision reaches at most 10 deploys back.
- **Final snapshot name:** with `db_protect = true` the final snapshot is
  `<name>-final`; a second destroy needs that snapshot deleted or renamed first.
- **Task definitions the deploy registered** stay in the account after
  `terraform destroy`; they cost nothing.
- **Before production:** ALB access logs and deletion protection, WAF, Multi-AZ
  RDS, customer-managed KMS keys and longer log retention, all left out here for
  cost and simplicity.
